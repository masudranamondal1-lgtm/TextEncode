# TextEncode

**A research-centred Digital Humanities workstation for textual annotation, entity modelling, relational analysis and scholarly data export.**

TextEncode is a local, research-oriented web application built with Python, Streamlit and SQLite. It helps researchers transform literary, historical and cultural texts into structured research data while keeping scholarly interpretation and verification in human hands. It is particularly suited to Bengali and English textual research, comparative literature, environmental humanities, historical research, spatial humanities and studies of relationships between people, places, institutions, material culture and ecological entities.

> **Development status:** Active development. The application entry-point docstring identifies the current app as v0.6, while the database module identifies itself as v0.5. Additional compatibility and feature revisions coexist in `app.py`. These are development labels, not a guarantee of a formally tagged stable release. Features and data structures may change.

## Vision

TextEncode aims to make the transition from close reading to computationally assisted research more transparent, reproducible and accessible. Literary and historical texts are not merely collections of words: they contain references to people, communities, rivers, landscapes, institutions, material objects, economic activities, ecological processes and historical events. These elements appear in particular contexts and enter into relationships that may change across texts, periods and geographical locations.

TextEncode provides a research environment in which researchers can identify these elements, describe them, link them to textual occurrences, connect them through explicit relationships, analyse patterns and export the resulting data for further work.

The long-term vision is an extensible environment connecting:

- Textual scholarship and close reading.
- Entity and relationship annotation.
- Bengali and multilingual language processing.
- Corpus-based and comparative analysis.
- Network analysis and spatial humanities.
- Evidence-centred interpretation and provenance.
- Machine-readable scholarly editions and research datasets.

TextEncode assists research; it does not automate scholarly judgement.

## Research philosophy

### Researcher-led interpretation

Automated recognition can suggest possible entities and phrases, but a suggestion is not a verified finding. Researchers review, correct, accept, reject or defer machine-generated candidates.

### Textual evidence and traceability

An entity must be distinguishable from the particular textual mentions through which it appears. Relationships are research claims to be interpreted and supported with evidence, not unquestionable facts generated by software.

### Relational understanding

The significance of an entity often emerges through its relations with other entities. A river, for example, may be represented through relationships with settlements, agriculture, transport, memory, institutions, animals and ecological change. TextEncode makes such relations available for structured analysis.

### Plural and extensible taxonomies

Different research questions require different classifications. TextEncode therefore supports configurable entity categories, relationship types and metadata definitions.

### Interoperability

Research data should not remain trapped inside one application. TextEncode provides export pathways for XML, graph and geospatial tools, as well as JSON and CSV.

## Core research workflow

1. **Create a research project.** Give it a name and description.
2. **Create or select a corpus.** A corpus groups documents within a project.
3. **Import source texts.** Upload Markdown or UTF-8 plain-text documents.
4. **Inspect parsed text.** TextEncode segments documents into passages and stores passage-level offsets.
5. **Configure a taxonomy.** Define entity categories and relationship types.
6. **Register entities.** Create canonical records for people, places, rivers, institutions, ecological entities and other research objects.
7. **Annotate mentions.** Link exact words or phrases in passages to canonical entities.
8. **Review recognition candidates.** Run Bengali candidate-recognition rules and make explicit researcher decisions.
9. **Create relationships.** Record relationships between entities within a selected document.
10. **Attach evidence.** Add source text and contextual information to support an interpreted relationship.
11. **Analyse the corpus.** Explore text statistics, keyword contexts, networks and mapped entities.
12. **Export research data.** Continue analysis in tools such as Gephi and QGIS or use the XML/JSON outputs elsewhere.

The sequence is flexible. Researchers can register entities manually before candidate recognition, and can annotate documents without creating relationships.

## Features

### Projects and corpora

The research organisation structure is **Project → Corpus → Document**. A project represents a research undertaking; a corpus groups documents within it; a document is an imported source text. The current application supports creating projects with an initial default corpus and selecting a project and corpus during document import.

### Document import and parsing

Supported upload extensions are `.md`, `.markdown` and `.txt`. Files are decoded as UTF-8, with a UTF-8 byte-order mark handled during import. Markdown parsing uses `markdown-it-py` and recognises headings, paragraphs, list items, blockquotes and fenced code blocks.

Each passage is stored with a passage identifier, sequence number, type, heading path, source text, plain-text representation, character offsets and content hash. Exact duplicate source text is detected using a SHA-256 hash.

**Offset caution:** The parser normalises line endings before parsing. When source files contain CRLF line endings, developers should verify document-level offsets against the stored source. Mention offsets are validated against the stored passage text.

### Document reader

The reader provides document selection, passage-based pagination, annotation highlighting, passage identifiers and adjustable reading preferences. Four display modes are available: Classic Light, Dark Research, Eye Comfort and High Contrast. Font size, line spacing and reading width are adjustable. Bengali and Latin-script typography are configured in the interface.

### Entity catalogue

An entity is a canonical research object, not a single occurrence of a name. Entity records can include canonical name, category, alternative names, description, notes and geographic coordinates.

The default taxonomy contains twelve broad categories:

1. Person
2. Plant
3. Animal
4. Place
5. River or hydrological feature
6. Institution
7. Material object
8. Economic activity
9. Event
10. Cultural practice
11. Ecological entity
12. Other

Researchers can extend the taxonomy with categories and subcategories.

### Mentions and annotation

A mention represents a specific occurrence of an entity in a document. It is associated with a canonical entity, document, passage, exact surface form, start and end character positions, verification status and optional research note. The database validates offsets against the passage text before saving. The interface supports exact word/phrase annotation and selection of a particular occurrence when a phrase appears more than once.

### Relationships and evidence bundles

Relationships connect two canonical entities through a defined relationship type. Default types include relations such as `inhabits`, `depends_on`, `affects`, `uses`, `governs`, `trades_with`, `protects`, `remembers`, `represents`, `transforms` and `connected_to`. Researchers can add relationship types and specify directionality.

A relationship can contain a description, document association, research assessment and supporting evidence. Evidence bundles currently support three domains: Literary, Historical and Geographical. Each stores source text and context. This is an initial evidence-recording mechanism, not a complete citation manager or provenance system.

### AI Candidate Review

The candidate-review workflow is designed for assisted annotation and human verification. The current Bengali candidate-recognition implementation is rule-based. It uses Bengali token recognition, stopword and classifier lists, verb-ending rules, case-marker stripping, known entities, title patterns and head-noun/compound heuristics.

Researchers can run recognition on a document, inspect candidates in context, choose a suggested word or phrase, confirm or change its category, link it to an existing entity, create a new entity, reject it or defer the decision. Phrase suggestions are generated from the recognised span and nearby whitespace-delimited tokens; they are not the output of a full Bengali phrase parser.

**Terminology note:** The interface calls this “AI Candidate Review”, but the current recognition engine is deterministic and rule-based. It does not currently call a remote large language model or use transformer-based named-entity recognition. Confidence values are heuristic scores, not calibrated probabilities.

### Taxonomy Manager

Taxonomy configuration includes entity categories and subcategories, relationship types, relationship directionality, custom metadata field definitions and JSON export of a taxonomy profile. Metadata definitions currently describe fields for entities or relationships; they are not yet a complete dynamic attribute-value editing system.

### Trash and recovery

Documents, entities, mentions and relationships have soft-deletion mechanisms at database level. The application provides recovery workflows for deleted documents and entities. The current interface also exposes confirmed permanent deletion for trashed documents and entities. Permanent deletion can remove dependent research records; keep a separate database backup before using it.

## Data model

TextEncode distinguishes source text, entities described in it, their textual occurrences and relationships interpreted by the researcher.

| Object | Meaning |
|---|---|
| Project | Top-level research container |
| Corpus | Group of documents within a project |
| Document | Imported source text |
| Passage | Parsed section of a document |
| Taxonomy profile | Reusable classification configuration |
| Entity category | Class assigned to a canonical entity |
| Entity | Canonical research object |
| Mention | Specific occurrence of an entity in a passage |
| Relationship type | Defined kind of relation |
| Relationship | Researcher-defined connection between entities |
| Evidence bundle | Supporting source text and context |
| Entity candidate | Machine-suggested annotation awaiting review |
| Audit log | Intended record of data operations |

Conceptually:

```text
Project
  └── Corpus
       └── Document
            └── Passage
                 └── Mention ───── Entity
                                      │
                                      └── Relationship
                                             └── Evidence Bundle

Taxonomy Profile
  ├── Entity Categories
  ├── Relationship Types
  └── Attribute Definitions
```

An entity may have multiple mentions across passages and documents, allowing the same canonical entity to be studied across a corpus. The current schema uses SQLite foreign keys for important associations and enables foreign-key enforcement on database connections.

The default database is `textencode.db` in the repository root. It is excluded from Git because research data should not be committed accidentally.

## Bengali text processing and candidate recognition

TextEncode contains more than one linguistic-processing component; they serve different purposes.

### Text statistics and tokenisation

The analysis pipeline uses lightweight Bengali/English tokenisation for word frequency, n-grams and basic text statistics. These are exploratory measures, not a linguistically validated morphological analysis.

### Bengali candidate-recognition engine

The modular engine in `modules/bengali_nlp/` includes Bengali token recognition, stopword and classifier filtering, verb-ending heuristics, case-marker stripping, known-entity matching, title-based person-candidate suggestions, and head-noun/compound-modifier heuristics. It is CPU-friendly and does not require a transformer model or external AI API.

Its output is a candidate list. Bengali morphology, compounds, inflection, spelling variation, named entities and contextual ambiguity require expert review.

### Unicode and offsets

Bengali text contains combining marks and orthographic features that can make naive tokenisation unreliable. The analysis modules use different tokenisation strategies for their respective tasks. For scholarly annotation, a key invariant is that stored start and end positions identify the exact surface form in the passage. Preserve source text and avoid normalising or rewriting passage text after annotations have been created unless performing a deliberate migration.

## Research analysis

### Text Analysis

The Text Analysis page supports analysis over all active documents, one project, one corpus or one document. Available analyses include:

- **Overview:** word count, unique words, character count, non-whitespace character count, sentence count and average sentence length.
- **Word frequency:** most frequent terms with an adjustable result limit.
- **N-grams:** bigrams, trigrams and four-word sequences.
- **Keyword in Context (KWIC):** search for a term and inspect surrounding left and right context.

These measures use lightweight tokenisation and sentence splitting. They should not be treated as linguistically definitive counts, particularly for complex Bengali texts.

### Network Analysis

The Network Analysis page constructs an interactive graph from researcher-defined relationships. Entities are nodes and relationships are labelled edges. The page supports analysis within a document, corpus, project or across active documents. The GEXF export can be opened in [Gephi](https://gephi.org/) for further layout, filtering and visualisation.

### Spatial Analysis

Entities can be assigned latitude and longitude. The Spatial Analysis page displays georeferenced entities within the selected research scope. GeoJSON export can be opened in [QGIS](https://qgis.org/) and other GIS software. The current spatial implementation and exporter are point-based: although the database includes a geometry-type field, the exporter emits Point geometries. TextEncode does not automatically geocode place names.

## Export and interoperability

| Export | Purpose | Compatible tools / uses |
|---|---|---|
| Dataset JSON | Structured application data | Python, custom applications and archival workflows |
| TEI-oriented XML | Document text in a TEI namespace | TEI-aware editors and XML workflows |
| GEXF | Entity relationship network | Gephi |
| Nodes CSV | Entity/node attributes | Gephi, spreadsheets and Python |
| Edges CSV | Relationship/edge attributes | Gephi, spreadsheets and Python |
| GeoJSON | Point features for georeferenced entities | QGIS and GIS software |

### TEI XML

The current exporter creates XML with a TEI namespace, a basic `teiHeader`, document title and passage content. It is an initial TEI-oriented export, not a fully encoded scholarly edition. It does not yet encode the complete entity, mention, relationship or evidence model as TEI stand-off markup, and it is not automatically validated against a TEI P5 schema or project-specific ODD. Validate and, where necessary, transform the output before treating it as a formal TEI deliverable.

### GEXF and CSV

The network exporter produces a GEXF graph, node CSV and edge CSV. Review the selected export scope and resulting files before drawing conclusions from a network.

### GeoJSON

The spatial exporter includes entities with non-null latitude and longitude and writes them as GeoJSON Point features. Coordinate accuracy and provenance remain the researcher's responsibility.

TextEncode is designed to run locally. The current application does not implement multi-user authentication, role-based permissions or cloud database synchronisation. The interface imports Google Fonts through its stylesheet, so configured web fonts require an internet connection; the core Python application and local SQLite database do not depend on a remote AI service.

## Installation and running

### Requirements

- Python 3.10 or later.
- pip.
- Windows, macOS or Linux.
- A modern web browser.

SQLite is included with standard Python distributions in most installations.

### 1. Clone the repository

```bash
git clone https://github.com/masudranamondal1-lgtm/TextEncode.git
cd TextEncode
```

### 2. Create and activate a virtual environment

**Windows PowerShell**

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

If script activation is blocked by PowerShell policy, use the appropriate policy for your environment or activate from Command Prompt:

```bat
.venv\Scripts\activate.bat
```

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Upgrade pip and install dependencies

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

If installation fails, check the Python version and the specific pip error before installing packages individually.

### 4. Start the application

From the repository root, with the virtual environment activated:

```bash
streamlit run app.py
```

Streamlit will print a local URL, usually `http://localhost:8501`. Open it in a browser. On first launch, TextEncode initialises the SQLite database and creates the default research project/corpus and taxonomy profile when the corresponding tables are empty.

Stop the application with `Ctrl+C` in the terminal running Streamlit.

## Recommended research workflow

### Stage 1: Establish the project

Create a project for the research question. Create separate corpora when sources need grouping by author, period, genre, archive or another meaningful criterion.

### Stage 2: Prepare the texts

Use UTF-8 Markdown or plain-text files. Preserve original spelling and punctuation, use consistent headings, avoid unnecessary manual line-break changes, retain separate source copies and record bibliographic information in document metadata and your research records.

### Stage 3: Design the taxonomy

Start with the default categories and extend them to match the research question. River-centred research, for example, may need hydrological features, settlements, ecological entities, economic activities, institutions and cultural practices. Define relationship types before large-scale annotation and use consistent labels.

### Stage 4: Register and annotate entities

Create canonical entities and record aliases. Annotate exact textual occurrences. Do not create a new entity for every spelling variation when the occurrences refer to the same research object.

### Stage 5: Review candidate recognition

Run candidate recognition as an aid to discovery. Check each accepted candidate against its passage and research context. Reject false positives and defer ambiguous cases rather than forcing a decision.

### Stage 6: Record relationships and evidence

Describe relationships as interpretations supported by text or other sources. Distinguish a relationship explicitly stated in a literary passage from one inferred through historical or geographical research. Use evidence-domain and context fields to preserve that distinction.

### Stage 7: Analyse and export

Use text analysis to explore patterns, network analysis to inspect entity relations, and spatial analysis to explore georeferenced entities. Export data for specialised work in Python, Gephi or QGIS.

## Database and data management

### Backups

The database contains valuable research annotations. Before updating TextEncode, changing the schema or using permanent deletion, stop the application and create a secure backup.

**Windows PowerShell**

```powershell
Copy-Item textencode.db textencode-backup.db
```

**macOS / Linux**

```bash
cp textencode.db textencode-backup.db
```

If SQLite WAL mode is active, stop the application before a simple file copy, or use SQLite's backup facilities to create a consistent backup.

### Schema version and migrations

The database layer currently declares `SCHEMA_VERSION = 5` and records it through SQLite's `user_version` pragma. Initialisation creates missing tables and adds selected compatibility columns. This is not yet a comprehensive versioned migration framework. Back up the database before moving between development revisions, particularly when entity, relationship or annotation structures change.

### Research data and privacy

The database is local by default. Do not commit the database, source documents, restricted exports or Streamlit secrets to the public repository. The `.gitignore` excludes common database files, virtual environments, caches, exports and Streamlit secrets; review it when adding new data directories.

## Current limitations and development notes

TextEncode is an evolving research tool. The following limitations matter when evaluating its current implementation:

1. **Development-version consistency:** Application and database docstrings do not use the same version label. Adopt a single release/versioning convention.
2. **Documentation drift:** Some existing audit and roadmap documents describe earlier states. Project/corpus tables and evidence-bundle storage already exist in the current database schema.
3. **Rule-based Bengali recognition:** Candidate recognition is heuristic, not a complete Bengali morphological analyser or validated NER model.
4. **No remote LLM integration:** The current candidate-recognition path does not require an external AI API.
5. **TEI completeness:** The exporter creates a basic TEI-oriented structure, not a fully encoded and schema-validated TEI edition.
6. **Evidence provenance:** Evidence bundles are simple source-text/context records. Bibliographic references, source editions, page-level citations, evidence assessment and provenance need a richer model.
7. **Custom attributes:** Attribute definitions can be registered, but a complete interface for storing and validating arbitrary attribute values is not yet implemented.
8. **Spatial geometry:** GeoJSON currently supports points, not lines, polygons or river-network geometries.
9. **Database migrations:** Schema changes need a formal migration and rollback strategy.
10. **Application consolidation:** Some page functions and older UI modules coexist with newer implementations in `app.py`. Refactor into smaller page and service modules.
11. **Test-suite alignment:** Checked-in tests include expectations that do not match the current database/parser API in all cases. Reconcile and run the suite before claiming a passing test status.
12. **Local single-user model:** Authentication, multi-user collaboration, permissions and cloud synchronisation are not implemented.

These limitations do not prevent exploratory or pilot research use, but they should be considered when planning a production archive or publication-grade scholarly edition.

## Testing

The repository uses pytest. Run the suite from the repository root:

```bash
pytest
```

Run individual modules:

```bash
pytest tests/test_parser.py
pytest tests/test_db.py
pytest tests/test_processor.py
```

The checked-in tests cover database persistence, Markdown passage parsing, offsets, Bengali tokenisation and basic text statistics. **Test status is unverified in this audit:** the application and suite were inspected, but not executed in a clean environment. Some tests appear out of sync with current implementation, including a database deletion helper and parser line-ending expectations. Reconcile the tests and run them before reporting a passing status.

When adding features, test database persistence and foreign-key behaviour, Bengali Unicode and combining marks, passage and mention offset integrity, duplicate imports, soft deletion/restoration/permanent deletion, relationship scope and evidence association, export structure/encoding, and project/corpus/document filtering.

## Roadmap

The priorities below reflect the current codebase and architecture direction. They are development goals, not claims of completed functionality.

### Priority 1: Reliability and maintainability

- Establish consistent application and schema versioning.
- Reconcile the test suite with the current implementation.
- Consolidate duplicate page functions and legacy UI modules.
- Introduce explicit database migrations and backup/restore utilities.
- Improve transaction boundaries and integrity checks.
- Add automated export validation.

### Priority 2: Annotation and evidence architecture

- Strengthen entity-to-mention provenance.
- Improve candidate review, phrase selection and duplicate detection.
- Support richer evidence records and bibliographic references.
- Introduce evidence assessment and source provenance.
- Improve annotation status and audit history.

### Priority 3: Bengali NLP

- Improve tokenisation and morphological analysis.
- Add contextual grammatical classification.
- Evaluate recognition against manually annotated Bengali corpora.
- Support configurable recognition rules and lexicons.
- Explore optional transformer-based models while preserving researcher review.

### Priority 4: Corpus and comparative research

- Strengthen project/corpus/document filtering across modules.
- Add comparative analysis across selected documents and corpora.
- Introduce temporal attributes and temporal analysis.
- Improve entity resolution across spelling and transliteration variants.

### Priority 5: Scholarly interoperability

- Develop richer TEI P5 encoding, including entity and stand-off annotation.
- Validate exports against TEI P5 schemas and project-specific ODD customisations.
- Improve GEXF/GraphML and GIS exports.
- Support richer spatial geometries and river-network representations.
- Document stable import/export formats for external tools.

### Longer-term direction

- Optional OCR-assisted ingestion for scanned texts and PDFs.
- Configurable NLP pipelines for additional languages.
- Reproducible research reports and analysis snapshots.
- Stronger provenance and audit-log workflows.
- Multi-user collaboration and synchronisation, if required by future deployments.
